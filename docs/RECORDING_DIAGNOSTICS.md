# 长直播录制诊断

核对日期：2026-11-09；本机 bililive-go v0.8.3，FFmpeg 7.1。目标是支持一小时以上录制，保留压缩视频及 TXT / SRT；不是通过调高定时切段值假装解决断流。

## 18:09 长录制与场次接口复核

同一 FLV 的完整视频标签时间达到 8721.533 秒（2 小时 25 分 21 秒），扫描前后从约 5.907 GB 增至 5.917 GB，写入进程和文件身份均保持不变。当前组合可以持续写入两小时以上；该文件仍在录制，未以此宣称结束后的全片解码、压缩或字幕验收。运行设置依旧不限时长、不限大小、不因标题变化切段。没有重启录制器或主动测速。

另核对录制器本机接口：`GET /api/lives/{id}` 返回 `recorder_status.file_path`、`out_time_ms` 和 `file_size`；`GET /api/lives/{id}/history` 返回本机录制 session 的开始、结束和结束原因。进行中的 session 使用零值结束时间，其 `end_reason=normal` 不能解释为已正常结束。`out_time_ms` 实际是 FFmpeg 的微秒值，处理时需除以 1000 才得到毫秒。

这些接口为持久化记录文件切换及归档提供依据；本机录制 session 不等于罗盘经营场次 ID。历史接口目前没有各片段路径，不能凭相同主播名称就自动认定所有旧文件属于同场。整场合并和片段结束原因追踪尚未实现。

真实断流触发因素仍未隔离：现有超时样本受主动测速影响，其他结束缺少完整日志。可确认插件的续录碎片化和诊断遗漏，不能据此断言用户网络或带宽不足。原始证据仅保存在本机 logs 的 `recording-current-long-check-20261109.json` 与 `recording-session-api-20261109.json`。

## 已确认的行为

- 运行设置为 `max_duration=0`、`max_file_size=0`、关闭标题变化切段；FFmpeg 命令无 `-t` / `-fs` / segment。没有几分钟的总时长上限。
- `timeout_in_us=60000000` 对应 FFmpeg `-rw_timeout` 的 60 秒无数据等待，并非录制总时长。FLV 经过 bililive-go 的本机探测代理，改 FFmpeg 等待时间未必能改变上游连接的超时。
- 同一文件从 14:07:09 录至 14:32:11，进程持续约 25 分钟。14:32:11 出现“上游流读取中断 … operation timed out”和 FFmpeg “Error during demuxing: Operation timed out”，随后新文件续录，房间仍显示开播及录制中。
- 此次故障期间执行过主动 `networkQuality` 测速，会占带宽。因此该观测可证明超时后新建文件的行为，不能独立证明此前自然断流均因本机网络造成；也不能据测速代理状态断言直播流走同一代理。后续采用被动连接 / 文件增长 / 错误日志观察。
- 多个结束文件在压缩时报告 `Invalid NAL unit size`。这说明原录屏含无效视频包，但没有独立证据证明损坏由本机网络、CDN 或录制器中的哪一层引起。严格压缩校验失败会保留原件。
- 工作台压缩只处理已稳定、闲置至少 60 秒且无进程打开的文件；压缩、校验、删除前重复确认，命令无时间限制。未发现平台后处理主动截短录屏的证据。
- 当前磁盘仍有约 43 GiB；11 月 6 日曾有磁盘满错误，不能用来直接解释本次短片。

## 15:52 补充核验：末尾半包与日志遗漏

结论：当前组合能够保存接近一小时的单文件；碎片化来自每次拉流结束后另建文件，且录制链路对中途结束的数据包缺少有效收尾。已经确认软件侧存在这些行为，但尚不能确定每次上游连接为何结束，也不能归因于用户的网络带宽不足。

### 真实文件的只读检查

14:32:11 开始、15:32:17 结束的文件为 2,435,364,772 字节，媒体时长约 59 分 52.73 秒。15:43:23 严格压缩失败，原件仍在；不是压缩成功或一小时以上成品验收通过。

对四个已经结束的文件逐个检查 FLV 标签边界及 H.264 NAL 长度，均仅在最后一个 AVC 数据包发现长度不完整，随后是 20 字节的结束标签：

| 文件开始时间 | 异常包媒体时间 | NAL 声明长度 / 剩余可用字节 |
|---|---|---|
| 14:06:37 | 00:00:28.800 | 26,089 / 12,288 |
| 14:07:09 | 00:22:01.699 | 24,230 / 4,096 |
| 14:32:11 | 00:59:52.731 | 28,727 / 12,288 |
| 15:32:17 | 00:11:39.734 | 14,726 / 0 |

此扫描只验证容器与 NAL 长度，不等同于完整解码。正在录制的文件尾部暂时不完整是正常现象，不作为损坏样本。

对接近一小时的文件，额外只读传送异常包之前的 2,435,352,440 字节给 FFmpeg，以 `-xerror -err_detect explode` 完整解码视频及音频。结果：退出码 0、107,779 帧、最终进度 `00:59:52.733333`；原文件 inode、大小、修改时间均未变化。测试排除了末尾 12,332 字节，没有生成替代成品、修改或删除原件。这说明该文件大部分内容可解码；不代表损坏尾包得到恢复，也不能据此证明音画同步或断流缺口已经解决。

15:44:02 又出现一次自然结束并续录（未执行主动测速）；此处仍没有明确超时日志。因此不能把全部切段都解释为 14:32:11 的同一种超时。

### 无网络复现与源码证据

用同一 FFmpeg 7.1 在临时目录生成 3 秒 AVC/AAC FLV，对照完整输入和在最后一个视频包中截断的输入：

- 完整输入：`-c copy` 退出码 0，严格解码退出码 0。
- 截断输入：`-c copy` 仍退出码 0，但记录 `Packet corrupt`、`Invalid NAL unit size`、`corrupt input packet`；其输出严格解码失败。测试不经过网络，临时样本已清理。

这复现了“输入突然结束 → 残包被写入文件 → 录制命令正常退出 → 后续严格压缩失败”。它证明当前组件的收尾行为存在缺口，不能单独判定真实输入中断来自 CDN、本机网络还是代理链路。

官方 v0.8.3 对应提交 `230e24d17c865ebadb86c74781913ec325f07f28`：

- [StreamProbe](https://github.com/bililive-go/bililive-go/blob/v0.8.3/src/pkg/streamprobe/probe.go) 逐块转发上游；EOF 和 context 取消直接返回，不记录“上游读取中断”；没有一小时总时长限制。普通 EOF 因而可能在现有日志中没有结束原因。
- [日志过滤器](https://github.com/bililive-go/bililive-go/blob/v0.8.3/src/pkg/utils/logger_writer.go) 在非 Debug 模式只保留含 `error/fatal/fail/exception/warning/warn` 的行。上述四类坏包提示均不含这些词，会被过滤掉。“日志没有报错”不能当作文件健康证明。
- FFmpeg 解析器使用 `-c copy`，没有对最后一个数据包做完整性处理；录制循环在解析结束后重新取流、创建新文件。已有 `fix_flv` 报告成功，但这四个样本之后仍存在末尾 NAL 错误，不能用该状态替代全片校验。

### 修复方向与验收边界

1. 明确保存每次结束原因（EOF、超时、用户停止、源站下播、坏包）及断流时间，不丢弃 `corrupt`、`Invalid NAL` 等诊断信息。
2. 对经过确认的末尾半包提供可审计恢复路径，保留原件，记录损失范围；恢复后仍需严格全片解码，禁止通过取消校验掩盖损坏。
3. 同一真实场次的重连片段归档并合并，保留缺口记录；不能简单拼接 FLV 文件，也不能恢复未接收到的画面。
4. 验收超过一小时的压缩成品、TXT/SRT 及原件清理；目前尚未实现并部署以上修复。

原始证据仅保存在本机 LiveOps 日志目录：`recording-packet-audit-20261109.json`、`recording-valid-prefix-decode-20261109.json/.log`、`recording-local-eof-reproduction-20261109.json`。不上传录屏、字幕或账号信息。
