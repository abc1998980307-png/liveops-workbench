# 长直播录制诊断

本记录说明长直播录制与断流恢复的技术边界。原始证据只保存在本机运行数据目录。

## 录制与场次接口

已观察到同一 FLV 文件持续增长，录制进程和文件身份保持不变，说明当前组合没有固定的短时长上限。运行设置保持不限总时长、不限文件大小、不因标题变化切段。进行中的文件不能作为结束后完整解码、压缩或字幕验收的证据。

录制器的 `GET /api/lives/{id}` 提供当前文件路径、输出时间和文件大小，`GET /api/lives/{id}/history` 提供本机录制 session 的开始、结束及结束原因。进行中 session 的零值结束时间和默认 `end_reason=normal` 不能解释为已结束。`out_time_ms` 实际是 FFmpeg 微秒值，处理时需除以 1000 才得到毫秒。本机录制 session 也不等于罗盘经营场次 ID；不能凭相同主播名称推断旧片段属于同场。

## 断流与坏尾包

- `max_duration=0`、`max_file_size=0` 和关闭标题变化切段用于取消总时长限制。FFmpeg 的 `-rw_timeout` 是无数据等待时间，不是录制总时长。
- 某次上游读取超时后，录制器新建文件续录，房间仍显示开播。该次观测同时存在主动网络测速，因此不能据此归因日常断流。另有自然结束未留下明确超时日志，说明结束原因仍需补齐。
- 已结束的部分 FLV 文件在最后一个 AVC 数据包存在不完整 NAL，严格压缩校验会失败并保留原件。正在录制的文件尾部暂时不完整是正常现象，不作为损坏样本。
- 对受影响样本只读检查容器和 NAL 边界，并对坏尾包之前的内容做严格全片解码。前段可解码不代表坏尾包已恢复、音画同步或断流缺口已解决。
- 无网络合成 FLV 复现了输入中断后残包被写入、录制命令正常退出但产物严格解码失败的行为。这证明组件收尾存在缺口，不能判定真实输入中断来自 CDN、本机网络还是代理链路。

bililive-go 的 [录制循环](https://github.com/bililive-go/bililive-go/blob/v0.8.3/src/recorders/recorder.go) 在解析结束后尝试下一次录制；[StreamProbe](https://github.com/bililive-go/bililive-go/blob/v0.8.3/src/pkg/streamprobe/probe.go) 对部分 EOF 路径没有明确结束日志；[日志过滤器](https://github.com/bililive-go/bililive-go/blob/v0.8.3/src/pkg/utils/logger_writer.go) 在非 Debug 模式可能过滤坏包提示。没有错误日志不能作为文件健康证明。

## 后处理与验收边界

工作台仅处理稳定、空闲且未被进程打开的文件；压缩、校验、删除前重复核对身份。显式的 FLV 末尾残包恢复会保留损坏原件，记录移除范围，并对压缩结果严格全片解码；中间损坏、编码不匹配、路径异常和正在录制的文件均拒绝恢复。TXT/SRT 按实际音轨约束字幕尾部，零时长识别结果不虚构显示时长。

本机曾对短、长样本验证恢复、压缩、解码和转写，另有连续长录制完成压缩及字幕流程。识别文字尚未逐句校对，真实多片段合并、断流缺口解释与每次结束原因仍需单独验收。归档只合并经身份校验的片段，并标记未知间断；不能恢复未收到的画面。

后续验收应在没有主动测速等竞争负载时记录自然断流原因，区分连接超时、源站结束、解析错误和房间状态变化；核对真实多片段归档的音视频与字幕偏移；继续验证长录制成品、原件清理和识别准确性。不得通过关闭严格校验或设置固定时长来掩盖断流。
